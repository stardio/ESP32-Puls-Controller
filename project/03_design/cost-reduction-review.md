## 0. 요약

| 항목 | 판단 |
|---|---|
| 절감안 A (S3 + W5500) | **기술적으로 조건부 타당.** 2축 펄스 자원(MCPWM 2그룹, PCNT 4유닛)은 문서로 확인했고, 펄스는 하드웨어가 생성하므로 CPU 클록 차이(400 → 240 MHz)는 결정 요인이 아니다. 다만 1 MHz 실적(D-028)은 P4에서 얻은 것이라 S3로 넘어오지 않는다. S3는 단축·2축 모두 미실측이 된다. W5500은 ESP-IDF 5.5.3에 드라이버가 포함되어 있고(servo1axis가 이미 사용 [E2][E8]), MACRAW + lwIP 방식이라 W5500 하드웨어 소켓 8개 제한이 Modbus 접속 수를 묶지 않는다. 남은 위험은 SPI 처리량, GPIO ISR 서비스 공유로 인한 간섭, 브로드캐스트 수신 부하이며, 모두 실측해야 한다 |
| 절감안 B (TCP/RTU 분리) | **사용자 결정(D-033·D-034 기록 예정)을 전제로 구현 가능.** 공용 PCB 1종에서 TCP 모델은 RS-485부, RTU 모델은 이더넷부를 미실장한다. RTU 모델은 패널이 마스터, 컨트롤러가 슬레이브다. 외부 장치용 RTU 마스터를 제품에서 빼므로(D-033) 포트 충돌은 없다. 115,200 bps에서 2축 운전 화면 1주기는 약 39 ms, 명령 응답은 최악 약 33~45 ms [산술]다. 레지스터 맵은 두 모델 공통으로 쓴다. RTU 슬레이브의 펄스 간섭 위험은 낮다(코어 분리, IRAM 설정). **D-017·D-019 대체와 SRS v0.8 개정(G2 변경 승인)이 필요하다**(§4.9) |
| A와 B의 관계 | P4 보드(F1)에는 IP101·RJ45가 보드에 붙어 있어 RTU 모델에서도 이더넷을 미실장할 수 없다. 그래서 P4 기준에서 D-034로 얻는 절감은 TCP 모델의 RS-485부뿐이다. RTU 모델의 이더넷 절감은 A(W5500을 캐리어에 실장)를 채택할 때만 생긴다 |
| 권고 | (1) A는 즉시 기준선을 바꾸지 않는다. 시험 펌웨어에 S3 포트를 추가해 P4와 같은 시험(T-03~T-09)과 신규 T-15~T-19를 S3에서 실측하고, PS-30 원가 결과와 함께 G3에서 결정한다(DC-20). 이를 위해 D-030(2축 실측 보류) 해제가 필요하다. (2) B는 D-034대로 진행한다. 모델 판별은 식별 저항 2비트 + 실장 감지 교차 확인(단일 바이너리), 레지스터 맵 공통, PC 도구·펌웨어 갱신 경로는 두 모델 공통 USB, EOL 검사는 실장된 포트로 `model_code`를 읽어 대조한다(DC-24~DC-29) |
| 새 결정 후보 / 실측 항목 | **DC-20~DC-29 10건, T-15~T-20 6건**, parts-selector 재조사 PS-30~PS-32 3건 |

### 1.2 GPIO 수

| 항목 | 값 | 근거 |
|---|---|---|
| S3 칩 GPIO | 45개(GPIO0~21, 26~48) | [R1] "45 GPIO". 번호 구간은 [산술](22 + 23 = 45). GPIO22~25는 S3에 없다 |
| 사용 제한 핀 | 내장/외장 플래시·PSRAM용 GPIO26~32, 옥탈 PSRAM 탑재 모듈의 GPIO33~37(제3자 자료는 35~37만 명시), 스트래핑 GPIO0·3·45·46, USB GPIO19·20, 콘솔 UART0 GPIO43·44 | [R12](제3자), [R1] §핀 정의 **원문 대조 필요** |
| 2축 필요 수 | 약 26(architecture §4.3 [산술]) + W5500 4~6(SCK·MOSI·MISO·CS 필수, INT·RST 선택) = **약 30~32** [산술] | architecture §4.3, [E2] |
| 사용 가능 추정 | 옥탈 PSRAM 미탑재 모듈: 45 − 7(26~32) = 38. 옥탈 PSRAM 탑재: 33. 이 중 스트래핑 4개는 출력·풀업 조건을 지키면 쓸 수 있다 [가정] | [산술], 모듈별 노출 핀 수는 **미확인**(PS-30) |
| 판단 | **옥탈 PSRAM 미탑재 모듈이면 가능**(약 38 대 30~32). P4 보드의 잔여 GPIO 27개(판매처 표기) 대비 여유가 늘어나 R-18(2축 GPIO 여유 약 1개)이 완화된다. 옥탈 PSRAM 탑재 모듈이면 여유 1~3개로 P4와 비슷하다. 펌웨어 RAM 요구로 PSRAM이 필요한지는 미확인이나, lwIP + 접속 6~8개 + 2축 상태를 내장 SRAM으로 감당할 수 있다고 본다 [가정] → DC-23 |

- **핀 번호는 전부 다시 정해야 한다.** servo1axis와 시험 펌웨어의 P4 핀 중 PULSE GPIO25, RS-485 TX GPIO24, START GPIO54, PHY 리셋 GPIO51은 S3에 없다. DIR GPIO32, Enable GPIO33, 보조 출력 GPIO26·27은 S3의 플래시·PSRAM 구간이다. hardware.json의 W5500 핀(SCK4·MOSI2·MISO3·CS5·INT6·RST14) [E7]은 S3에도 있지만, GPIO3이 스트래핑 핀이라 MISO로 쓰기에 부적합하다 [R12, 원문 대조 필요]. 또 SPI2 전용(IO MUX) 핀이 아니어서 GPIO 매트릭스를 거친다(§2.3).

### 1.3 판단

| 목표 | 판단 | 이유 |
|---|---|---|
| 2축 동시 축당 ≥ 200 kpps (D-010, NFR-002) | **자원상 가능, 성능 미실측** | MCPWM 그룹 2개와 PCNT 유닛 4개로 축당 1세트를 배정할 수 있다. 200 kHz는 10 MHz 해상도에서 50틱이라 양자화 문제가 없다 [산술]. P4도 2축은 미실측이므로(D-030) 근거 수준은 P4와 같다. 다만 P4에는 단축 실적이 있고 S3에는 없다 |
| 1축 1 MHz (D-028 수준) | **하드웨어상 가능성 높음, 실적 없음** | 출력은 MCPWM이 하드웨어로 만든다. 클록원이 P4와 같은 160 MHz이고(10 MHz 해상도에서 10틱 [산술]), PCNT 블록 누적 ISR 빈도는 1 MHz에서 축당 약 33회/s라 부담이 작다 [산술]. 미확인으로 남는 것은 PCNT 입력 최대 주파수와 주기 레지스터 폭이다. **D-028은 P4 실적이므로 S3 제품에는 "검증 사실"로 표기할 수 없다(D-031).** T-15·T-19로 다시 실측해야 한다 |
| 목표 정지 ISR(f_stop_max 불변식) | 영향 작음 [가정] | 감속 끝 주파수 ≤ 5 kHz [가정]이면 허용 지연은 약 200 µs [산술]다. 240 MHz Xtensa에서도 ISR 지연은 그보다 훨씬 작을 것으로 본다 [가정]. 실제 값은 T-08(S3 빌드)과 T-17(W5500 인터럽트 간섭)로 확인한다 |
| 플래시 쓰기 간섭(R-16) | P4와 같은 위험 | 플래시 작업 중 캐시가 꺼지는 구조는 같다. IRAM 안전 설정 파일 [T4]의 옵션 이름은 ESP-IDF 드라이버 공통 옵션이라 S3에도 적용된다 [가정, 빌드 시 `grep IRAM sdkconfig`로 확인]. 추가로 SPI 마스터 ISR의 IRAM 배치(`CONFIG_SPI_MASTER_ISR_IN_IRAM`) 확인이 필요하다 |

### 1.4 시험 펌웨어(project/04_code/test-fw) S3 이식 범위

시험 펌웨어는 순수 로직(`tfw_logic`: 프로파일·주기 계산·레지스터 창·Modbus PDU, 호스트 시험 가능)과 ESP-IDF 드라이버 사용부가 분리되어 있다. MCPWM·PCNT·GPTimer·GPIO 드라이버 API는 칩과 무관한 ESP-IDF 공통 API다. 이식은 "포트 계층 교체"가 아니라 **설정·핀·이더넷 초기화 교체** 수준이다.

| 파일 | 변경 | 내용 |
|---|---|---|
| sdkconfig.defaults [T5] | 수정 | `CONFIG_IDF_TARGET="esp32s3"`, 플래시 크기(모듈에 맞춤, 32 MB → 미정), `CONFIG_ESP_DEFAULT_CPU_FREQ_MHZ_240`, `CONFIG_ETH_SPI_ETHERNET_W5500=y`, `CONFIG_LWIP_MAX_SOCKETS` 상향(DC-27), 콘솔 설정. 칩 리비전 최소값(P4 v3.1) 제거 |
| sdkconfig.tfw_iram_on [T4] | 확인 + 추가 | 기존 8개 옵션 유지(존재 확인). SPI 마스터 ISR IRAM 옵션 추가 검토 |
| main/Kconfig.projbuild [T3] | 수정 | 축1·축2·비상정지·디버그 GPIO 기본값을 S3 핀맵으로. W5500 핀(SCK·MOSI·MISO·CS·INT·RST)과 SPI 클록, INT/폴링 선택(`poll_period_ms`) 항목 추가 |
| components/tfw_pulse2/tfw_pulse2.c [T2] | 소폭 수정 | MCPWM·PCNT·GPTimer 코드는 그대로 쓴다(`group_id = 축 번호`는 S3 그룹 2개와 맞음). P4 전용 예약 핀 상수 목록(51, 23, 26, 27, 46)을 S3 예약 핀으로 바꾼다. `probe_caps`는 그대로 쓰고 결과로 S3 자원을 기록한다 |
| components/tfw_estop_io/tfw_estop_io.c | 소폭 수정 | API는 같다. 인터럽트 레벨 1~3은 Xtensa C 처리기 범위에서 유효하다 [가정]. **GPIO ISR 서비스를 W5500 INT와 공유하게 되므로 설치 코어·레벨을 다시 정해야 한다**(§2.4, DC-22) |
| components/tfw_modbus/tfw_modbus.c [T6] | **이더넷 초기화 교체** | 내장 EMAC·IP101 초기화(`esp_eth_mac_new_esp32`, `esp_eth_phy_new_ip101`, PHY 리셋 GPIO51)를 SPI 버스 초기화 + `esp_eth_mac_new_w5500`/`esp_eth_phy_new_w5500` + MAC 주소 설정으로 바꾼다. servo1axis의 `start_w5500_interface()` [E2]를 복사해 쓰면 된다(원본 수정 금지). esp_netif 이후 lwIP 소켓 서버(접속 수 상한, 시험 창)는 **변경 없음**. 보조 출력 GPIO 23·26·27·46 상수는 S3 핀으로 바꾼다 |
| main/tfw_main.c | 확인 | 칩 정보·CPU 클록 조회(`esp_chip_info`, `esp_clk_tree`)와 코어 배치는 칩 공통이다. 부팅 로그의 P4 리비전 해석 문구만 정리한다 |
| tools/check_iram.sh | 수정 | `riscv32-esp-elf-nm/objdump` → `xtensa-esp32s3-elf-*`. IRAM 주소 범위 판정값(P4 0x4FFxxxxx [가정])을 S3 값으로 바꾼다(S3 IRAM 주소 범위는 **미확인**, TRM 대조) |
| components/tfw_logic, host/(Python) | 변경 없음 | 기본 IP만 설정에 따라 다르다. 판정·보고 로직은 칩과 무관하다 |
| 빌드 구성 | 추가 | P4와 S3를 나란히 빌드할 수 있게 대상별 sdkconfig(`sdkconfig.defaults.esp32s3`)로 나누는 방식을 권고한다. 그러면 같은 시험을 두 칩에서 비교할 수 있다 |

### 2.2 소켓 수(8)와 T-05 6접속(D-029)

| 구현 방식 | 소켓 제한 | T-05(6접속, 빌드 8) | 시험 펌웨어 코드 영향 |
|---|---|---|---|

### 2.4 ISR·펄스 생성과의 간섭 위험

| # | 위험 | 내용 | 대책 | 확인 |
|---|---|---|---|---|
| W-1 | **GPIO ISR 서비스 공유** | 시험 펌웨어는 비상정지 입력을 `gpio_install_isr_service()` + `gpio_isr_handler_add()`로 처리하고 레벨 3(IRAM)으로 설치한다 [T7]. ESP-IDF W5500 드라이버도 INT 핀을 GPIO ISR 서비스로 받는 구조로 본다 [가정: 드라이버 원문 대조 필요]. GPIO ISR 서비스는 칩 전체에 인터럽트 하나라서, **수신 프레임마다 레벨 3 GPIO 인터럽트가 비상정지와 같은 코어에서 발생한다.** 그 코어가 실시간 코어(PCNT·GPTimer ISR, 레벨 2·1)이면 정지 ISR과 갱신 ISR을 선점한다 | (a) GPIO ISR 서비스와 W5500 INT를 통신 코어(0)에 둔다. 비상정지 2차(소프트웨어) 경로도 코어 0에서 돈다. 1차(외부 게이트)·1.5차(MCPWM 고장 입력)는 하드웨어 경로라 코어와 무관하다. (b) W5500 폴링 모드(`int_gpio_num = -1`, `poll_period_ms` 1~5 [가정])로 INT 인터럽트를 없앤다. 대신 응답 지연이 최대 폴링 주기만큼 늘어난다 | T-17에서 (a)·(b)를 비교한다(T-08 지연 분포, T-07 2차 경로 응답, NFR-010 응답 시간) |
| W-2 | SPI 전송 중 CPU 점유 | W5500 드라이버가 SPI 전송을 폴링 전송으로 하는지 인터럽트·DMA로 하는지 미확인이다. 폴링 전송이면 1,500바이트 프레임 하나에 20 MHz에서 약 0.6 ms 동안 해당 코어를 점유한다 [산술] | 드라이버 수신 태스크, SPI ISR, lwIP `tcpip` 태스크를 모두 코어 0에 고정한다(`CONFIG_LWIP_TCPIP_TASK_AFFINITY`, 드라이버 태스크 코어 설정 [가정: 설정 항목 존재 확인 필요]) | T-05(S3 빌드)에서 갱신 지연 초과 0과 `upd_max_us`로 확인 |
| W-3 | 브로드캐스트·멀티캐스트 수신 부하 | MAC RAW 모드에서는 프레임 필터링을 W5500 MAC 필터 설정에 맡긴다. 드라이버 헤더에 MAC 필터 비트가 정의되어 있으나 [R6], 활성화 여부와 브로드캐스트 처리 방식은 미확인이다. 공장망 브로드캐스트 폭주 시 SPI·lwIP 부하가 커진다. EMAC(P4)는 DMA로 받아 CPU 부하가 상대적으로 작다 | 코어 분리(W-2), 수신 큐 상한 [가정] | T-18(브로드캐스트 부하 중 펄스 오차 0, 링크 유지) |
| W-4 | 플래시 쓰기 중 SPI 이더넷 | NVS 쓰기 중 캐시가 꺼지면 IRAM이 아닌 코드가 멈춘다. 이더넷 수신이 잠시 멈출 뿐 펄스에는 영향이 없을 것으로 본다 [가정] | 운전 중 저장 보류(MOD-12, 기존 방침) | T-06(S3 빌드) |
| W-5 | SPI 버스 공유 | W5500 전용 SPI2 버스를 쓰면 플래시(SPI0/1)와 공유하지 않는다 [가정: S3 GP-SPI 구성 원문 대조] | 다른 SPI 장치를 같은 버스에 두지 않는다 | 설계 규칙 |

- 결론: 간섭은 **구조상 피할 수 있다**(코어 분리 + INT 경로 선택). 다만 W-1은 P4 기준선에는 없던 새 위험이라 실측이 필요하다(T-17).

## 4. 검토 4 — 절감안 B: TCP 모델 / RTU 모델 (공용 PCB, 부품 미실장으로 구분)

> **v0.1 갱신(2026-10-30, 사용자 결정 반영):**
> (1) RTU 모델에서는 터치패널이 RS-485 Modbus RTU 마스터, 컨트롤러가 슬레이브다.
> (2) 이더넷 포트와 RS-485 포트는 모두 **HMI 통신용**이다. servo1axis의 RS-485 RTU 마스터 기능(외부 장치 쪽)은 제품 범위에 넣지 않는다(**D-033 기록 예정**).
> (3) 공용 PCB 1종에서 부품 미실장으로 모델을 나눈다. TCP 모델은 RS-485부, RTU 모델은 이더넷부를 미실장한다(**D-034 기록 예정**).
> 이에 따라 이 절의 이전 권고("TCP 표준 + RTU 옵션 실장")는 철회한다. 아래는 D-034를 전제로 구현 조건을 정리한 것이다. D-033·D-034의 decisions.md 기록은 메인 세션 몫이다.

### 4.1 모델별 통신 구조

```
 [TCP 모델]  터치패널(Modbus TCP 클라이언트) ──유선 이더넷── 컨트롤러(Modbus TCP 서버, MOD-15)   RS-485부 미실장
 [RTU 모델]  터치패널(Modbus RTU 마스터) ──RS-485(2선)── 컨트롤러(Modbus RTU 슬레이브, MOD-16)  이더넷부 미실장
             ※ RTU 버스의 마스터는 패널 1대뿐. PC 도구는 별도 경로(§4.6)
```

| 항목 | 검토 |
|---|---|
| 패널 쪽 | 이지뷰(Weintek 여부 미확인)·M2I 5/7인치 후보 기종에 RS-485 COM 포트가 있는지, Modbus RTU 마스터로 동작하는지, 32비트 워드 순서 설정이 되는지는 **미확인**(PS-29 추가 요청, PS-32) |
| 컨트롤러 쪽 | RTU 슬레이브는 MOD-16(신규)으로 이미 계획되어 있다. PDU 처리는 MOD-14 공통이고 프레이밍(주소·CRC·3.5문자 간격)만 MOD-16이 맡는다 |
| 기존 RTU 마스터와의 포트 충돌 | **D-033으로 해소.** servo1axis의 RTU 마스터는 릴레이 보드 시험용이다(슬레이브 0xFF, FC05로 릴레이 1~4 전환, FC01·FC02 되읽기 [E3]). 제품에 넣지 않으므로 UART1·RS-485 포트는 슬레이브 전용이 된다. 같은 포트에서 마스터와 슬레이브를 겸하는 구성, 포트 2개 구성은 모두 필요 없다. 재사용하는 것은 UART·RS-485 반이중 설정 코드(`uart_driver_install`, `uart_set_mode(UART_MODE_RS485_HALF_DUPLEX)`, DE/RE 핀 [E3])뿐이고, 마스터 로직은 쓰지 않는다(architecture §3.2 MOD-05·16 대응과 같음) |
| 동시 접속 | RTU 버스는 마스터가 하나라서 패널과 상위 PLC·PC 도구를 동시에 쓸 수 없다. NFR-023(동시 접속)과 T-05 6접속 조건은 TCP 모델에만 적용한다 |

### 4.2 RTU 실제 속도에서 HMI 갱신 주기와 응답 지연 [산술]

계산 조건: 8N1(문자당 10비트) [가정, 패리티 사용 시 11비트로 약 10% 증가]. 115,200 bps는 문자당 86.8 µs, 9,600 bps는 1.042 ms. 프레임 간 간격 t3.5는 9,600 bps에서 3.5문자 = 3.65 ms, 19,200 bps 초과에서는 고정 1.75 ms로 잡았다 [가정: Modbus 직렬선 규격의 권고값으로 알고 있으나 원문 미대조]. 트랜잭션마다 간격 2회를 넣고, 컨트롤러 처리 시간은 1 ms [가정], 패널의 요청 간 대기 시간은 **미확인**이라 0으로 두었다.

| 트랜잭션 | 바이트(요청 + 응답) | 115,200 bps | 9,600 bps |
|---|---|---|---|
| FC03 32레지스터(레거시 창 0x0000~0x001F) | 8 + 69 = 77 | 6.7 + 3.5 + 1 = **약 11.2 ms** | 80.2 + 7.3 + 1 = **약 88.5 ms** |
| FC03 16레지스터(축 상태 블록 1축분 [가정 크기]) | 8 + 37 = 45 | 약 8.4 ms | 약 55.2 ms |
| FC01 코일 8개 / FC02 DI 8개 | 8 + 6 = 14 | 각 약 5.7 ms | 각 약 22.9 ms |
| FC03 125레지스터(최대) | 8 + 255 = 263 | 약 27.3 ms | 약 282 ms |
| FC05 코일 쓰기(시작·정지 명령) | 8 + 8 = 16 | 약 5.9 ms | 약 25.0 ms |

| 지표 | 115,200 bps | 9,600 bps | 비고 |
|---|---|---|---|
| 2축 운전 화면 1주기(레거시 32 + 코일 + DI + 축 상태 2축) | 11.2 + 5.7 + 5.7 + 8.4 × 2 = **약 39 ms(약 25 Hz)** | 88.5 + 22.9 + 22.9 + 55.2 × 2 = **약 245 ms(약 4 Hz)** | 패널 자체 스캔 주기·대기 시간이 더해진다(미확인) |
| 명령 응답 지연(최악) | 진행 중인 읽기 1건(최대 약 27 ms) + 쓰기 약 6 ms = **약 33 ms**. 패널이 쓰기를 주기 끝까지 미루면 약 45 ms | 약 282 + 25 = **약 307 ms**, 주기 끝까지 미루면 약 270 ms 이상 | 패널의 쓰기 우선 처리 방식은 미확인 |
| TCP 모델 대비 | 이더넷은 프레임 전송 시간이 µs 단위라 패널 스캔 주기가 지배한다. RTU 115,200 bps는 사람 조작 기준으로 충분할 것으로 본다 [가정]. 9,600 bps는 2축 화면에서 표시가 늦게 느껴질 수 있다 | — | NFR-010 요구값 미확인이라 합부는 판단할 수 없다 |

- 권고: RTU 모델 기본 통신 속도는 **115,200 bps**(후보, DC-25). 9,600·19,200 bps는 선택값으로 둔다. 화면 데이터는 2축 상태를 한 번의 FC03으로 읽을 수 있게 연속 블록으로 배치하는 것을 권장한다(MOD-23).
- JOG 유지 감시(FR-019, MOD-15 통신 두절 감시): RTU 모델의 감시 시간은 화면 1주기보다 충분히 길어야 한다. 9,600 bps에서는 약 245 ms 주기라 감시 시간 하한을 모델별 파라미터로 둔다 [가정] → MOD-16 개정 범위.

### 4.3 RTU 슬레이브 처리와 펄스 생성 ISR의 간섭

| # | 위험 | 내용 | 대책 | 확인 |
|---|---|---|---|---|
| U-1 | UART ISR 선점 | ESP-IDF UART 드라이버 ISR은 수신 FIFO 임계값과 수신 타임아웃(tout) 조건에서 발생한다. 115,200 bps에서 화면 1주기(약 39 ms)에 트랜잭션 5건이면 초당 약 130건 [산술]이고, 프레임당 ISR이 몇 회라 부하는 작다 [가정]. 다만 ISR이 실시간 코어에 할당되면 PCNT 정지 ISR과 GPTimer 갱신 ISR을 지연시킬 수 있다. ISR은 `uart_driver_install`을 호출한 코어에 할당된다 [가정: ESP-IDF 인터럽트 할당 규칙, 원문 대조] | UART 드라이버 설치와 MOD-16 태스크를 통신 코어(0)에 둔다. 인터럽트 레벨은 PCNT·GPTimer보다 낮게(레벨 1) 둔다 | T-20 |
| U-2 | 3.5문자 간격 판정 | 프레임 끝을 소프트웨어 타이머로 판정하면 고빈도 타이머 ISR이 생긴다 | UART 하드웨어 수신 타임아웃(tout, 문자 단위)으로 프레임 끝을 판정한다. 별도 타이머 ISR을 만들지 않는다. 115,200 bps에서 고정 1.75 ms 간격을 정확히 지키는지는 tout 설정 범위에 달려 있다(미확인) | T-20(프레임 경계 오판 0) |
| U-3 | 플래시 쓰기 중 수신 FIFO 넘침 | NVS 쓰기·지우기 중 캐시가 꺼지면 IRAM에 없는 UART ISR이 멈춘다. 115,200 bps에서 초당 약 11.5바이트/ms [산술]이므로, 수신 FIFO 크기(칩별 미확인)를 몇 ms 만에 채운다. 넘치면 프레임이 깨지고 패널이 재시도한다. 펄스 출력에는 영향이 없다(펄스는 하드웨어, 정지 ISR은 IRAM) | `CONFIG_UART_ISR_IN_IRAM` 사용, 운전 중 저장 보류(MOD-12, 기존 방침) | T-06과 T-20 동시 조건 |
| U-4 | DE/RE 전환 | 반이중 송수신 전환을 소프트웨어 GPIO로 하면 응답 끝 처리 지연이 생긴다 | `UART_MODE_RS485_HALF_DUPLEX`로 RTS 핀을 하드웨어가 제어하게 한다(기존 RTU 코드가 이미 이 모드 사용 [E3]) | T-20 |

- 결론: RTU 슬레이브는 W5500(TCP 모델, §2.4)보다 인터럽트 부하가 작다. 코어 분리와 IRAM 설정을 지키면 펄스 간섭 위험은 낮다 [가정]. 확정은 T-20.

### 4.6 펌웨어 모델 판별 방식

| 방식 | 장점 | 단점 | 판정 |
|---|---|---|---|
| (a) 빌드 옵션(모델별 바이너리) | 미실장 블록 코드를 빼서 크기가 작다 | 바이너리 4종 관리, 잘못된 바이너리를 기록할 위험, 현장 갱신 파일도 4종 | 비권고 |
| **(b) 부트스트랩(식별) 저항 2비트** | 단일 바이너리. BOM 변형과 1:1로 묶여 생산에서 함께 관리된다. 부팅 시 GPIO 2개를 읽기만 하면 된다 | GPIO 2개 소모(architecture §4.3 집계에 이미 포함). 칩 스트래핑 핀은 쓰지 않는다 | **기본** |
| (c) 실장 감지 | 잘못 조립한 것을 잡는다 | 이더넷은 감지 가능: A안은 W5500 버전 레지스터를 SPI로 읽는다 [가정: 레지스터 값 원문 대조]. P4 F1은 IP101이 항상 있어 구분이 안 된다. RS-485 트랜시버는 ID가 없어 감지 방법이 미확인이다 | **보조**(교차 확인용) |

- 권고: **(b) + (c) 교차 확인.** 코드 [가정]은 `MID[1:0]` = (축 수, 통신) → 00 = 1축 TCP, 01 = 1축 RTU, 10 = 2축 TCP, 11 = 2축 RTU. A안에서는 식별 저항 값과 W5500 감지 결과가 다르면 `E-HW-MODEL` 알람을 내고 운전을 막는다. P4 F1 기준에서는 (b)만 쓴다.
- 기동 동작(의사코드):

```
model = read_model_id_straps()                 // 2 GPIO, before any comm init
if model.comm == TCP:  start_ethernet(); start_modbus_tcp()        // MOD-04, MOD-15
else:                  start_uart_rs485(); start_modbus_rtu_slave() // MOD-05, MOD-16
if A-plan and (w5500_detected() != (model.comm == TCP)): raise E-HW-MODEL, block motion
expose model code in system register (read-only)
```

- PC 도구·펌웨어 갱신 경로(FR-016·FR-018): DC-09(PC 도구 = 이더넷)는 RTU 모델에서 성립하지 않는다. RTU 버스는 패널이 마스터라 PC 도구를 함께 물릴 수도 없다. **권고: 두 모델 모두 USB를 공통 PC 도구·갱신 경로로 둔다**(S3는 네이티브 USB [R12]. P4 F1은 보드 USB-C [P23]를 제품에서 쓸 수 있는지 미확인). TCP 모델은 이더넷 경로도 유지한다 → DC-25.

| 프로토콜 한계 | RTU 프레임 최대 256바이트에서 PDU 최대 253바이트는 TCP와 같다. 따라서 FC03 최대 125레지스터, FC16 최대 123레지스터로 한 번에 읽고 쓸 수 있는 범위가 같다 [가정: Modbus 규격 원문 미대조]. 32비트 하위 워드 먼저 규칙(DC-15)도 그대로 쓴다 |
| 국번 | TCP는 유닛 ID 1(기존 [E5]). RTU는 슬레이브 주소 `rtu_addr`(0x400C, interface-spec §5) 기본 1 [가정]. 레거시 창도 RTU에서 같은 주소로 열어, 기존 MT8051iP 화면의 주소 체계를 통신 설정만 바꿔 쓸 수 있게 한다 |
| 통신 전용 레지스터 | TCP 전용(IP·마스크·게이트웨이·`max_clients`, 0x0110~0x0114)과 RTU 전용(`rtu_baud`·`rtu_parity`·`rtu_addr`, 0x400A~0x400C)은 **두 모델 모두 주소를 유지**한다. 읽기는 저장값을 돌려주고, 쓰기는 저장하되 해당 인터페이스가 없는 모델에서는 쓰지 않는다. 예외 응답으로 막으면 맵이 모델별로 달라지고 PC 도구 백업·복원(FR-016)이 모델마다 갈라지기 때문이다 → DC-28 |
| 모델 레지스터(신규) | 시스템 영역에 읽기 전용 `model_code`(MID 2비트 + 실장 감지 결과 + 펌웨어 판별 결과)를 둔다. 주소는 interface-spec 개정 때 정한다. HMI·PC 도구·검사 지그가 이 값으로 모델을 확인한다 |
| HMI 화면 데이터 | 화면 주소는 공통이다. 다른 것은 패널 프로젝트의 통신 장치 설정(Modbus TCP/IP ↔ Modbus RTU, 국번, 속도)뿐이다. MOD-23 공통 정의에서 메이커별로 통신 설정만 다른 2벌을 만든다. 메이커 2종이면 모두 4벌이다(D-021·D-022 범위 증가) |

### 4.8 생산·검사 시 모델 구분

| 단계 | 방법 |
|---|---|
| BOM | 공용 PCB 1종 + BOM 변형 4종(1축 TCP / 1축 RTU / 2축 TCP / 2축 RTU). 미실장 목록(§4.5)과 식별 저항 배치를 변형별로 정의한다. 축2 미실장(DC-07)과 같은 방식으로 관리한다 |

### 4.9 SRS·결정 개정 필요 항목 (D-017·D-019 대체)
